# IPC layer

Code: `openxr/src/xrt/ipc/`. Used only when the runtime is built in the **out-of-process** topology (see [ARCHITECTURE.md](ARCHITECTURE.md)). Splits the OpenXR client (a thin proxy living inside the app's process) from `monado-service` (which actually owns the devices and compositor).

Reference docs upstream: `openxr/doc/ipc-design.md`, `openxr/doc/swapchains-ipc.md`.

## Transport

```
┌──────── app process ────────┐         ┌──────── monado-service ────────┐
│ libopenxr_monado            │         │ ipc_server (one thread per     │
│  -> ipc_client_*            │  AF_UNIX│  client) + shared memory       │
│       (proxy xrt_* impls)   │  (Linux)│                                │
│  ipc_message_channel_unix.c │◄────────┤  ipc_server_per_client_thread  │
│  ipc_message_channel_win.cpp│  named  │  ipc_server_mainloop_*         │
│                             │  pipe   │                                │
│  ipc_shmem.c                │  (Win)  │  ipc_shmem.c (mmap'd region)   │
└─────────────────────────────┘         └────────────────────────────────┘
```

* **Message channel** — `ipc_message_channel_unix.c` / `ipc_message_channel_windows.cpp`. Length-prefixed framed messages; supports fd / HANDLE passing alongside each message (for swapchain image handles, sync handles).
* **Shared memory** — one `ipc_shared_memory` region per service (see `ipc_protocol.h:191`), mmap'd into every client. Holds device descriptors, tracking origins, binding-profile arrays, input/output ID maps, and the per-client `ipc_layer_slot[IPC_MAX_SLOTS]` rings (128 slots, holding one frame's layer state each).
* **Sockets**: AF_UNIX abstract namespace on Linux, named pipe on Windows, AIDL Binder bridge on Android (`ipc/android/`).

## Protocol generation

The RPC surface is *generated*. Edit `ipc/shared/proto/*.json`, run the build, and `ipc_client_generated.{c,h}` + `ipc_server_generated.{c,h}` (plus a server dispatch table) get regenerated by `ipc/shared/proto.py` driving the templates in `ipc/shared/ipcproto/`.

Schema: `ipc/shared/proto.schema.json`. Each RPC declares typed `in[]` and `out[]` arrays:

```jsonc
// proto/50-compositor.json (excerpt)
"compositor_predict_frame": {
    "out": [
        {"name": "frame_id",                  "type": "int64_t"},
        {"name": "wake_up_time",              "type": "int64_t"},
        {"name": "predicted_display_time",    "type": "int64_t"},
        {"name": "predicted_display_period",  "type": "int64_t"}
    ]
},
"compositor_layer_sync": {
    "in":  [{"name": "slot_id", "type": "uint32_t"}],
    "out": [...]
}
```

Files in `ipc/shared/proto/`:
* `10-instance.json` — instance bring-up.
* `50-compositor.json` — frame predict / wait_woke / begin / discard / layer_sync / swapchain create+import.
* `50-device.json` — input/output sampling, set_output (haptics), feature_inc/dec.
* `50-future.json` — async futures (planes, anchors).
* `50-session.json` — `session_create`, `session_poll_events`, `session_begin/end/destroy`.
* `50-space.json` — locate, create offset/dev/relation/path/etc.
* `50-swapchain.json` — image create/import, acquire/wait/release.
* `50-system.json` — system properties, system_devices, roles, features.

The `10-` prefix orders connection bring-up before everything else; the file naming is purely how the generator sorts message IDs.

## Shared-memory layout

Lives in `ipc/shared/ipc_protocol.h` as `struct ipc_shared_memory` (line 191+). Contents:

* `u_git_tag` — service version string. Mismatch with client = abort.
* `itracks[]` — tracking origins, addressed by `tracking_origin_index`.
* `isdevs[IPC_MAX_DEVICES]` (`struct ipc_shared_device`) — device descriptors.
* Flat arrays of `xrt_input`, `xrt_output`, `ipc_shared_binding_profile`, `xrt_binding_input_pair`, `xrt_binding_output_pair`. Devices reference into them by `(first_*_index, *_count)`.
* `slots[IPC_MAX_SLOTS]` — per-frame layer slots used during `compositor_layer_sync`. The client picks a `slot_id`, writes the `ipc_layer_slot` payload (`layer_count`, `layers[IPC_MAX_LAYERS]`), and sends the RPC. The server reads the slot and forwards to the compositor.

Key constants (`ipc_protocol.h:34-47`):
* `IPC_BUF_SIZE = 2048` — message channel buffer size.
* `IPC_MAX_VIEWS = 8`.
* `IPC_MAX_FORMATS = 32`.
* `IPC_MAX_DEVICES = 8`.
* `IPC_MAX_LAYERS = XRT_MAX_LAYERS`.
* `IPC_MAX_SLOTS = 128`.
* `IPC_MAX_CLIENTS = 32`.

## Client side

`ipc/client/`. One proxy per `xrt_*` interface:

| File | Interface it proxies |
| --- | --- |
| `ipc_client_instance.c` | `xrt_instance` |
| `ipc_client_system.c` + `ipc_client_system_devices.c` | `xrt_system` + `xrt_system_devices` |
| `ipc_client_session.c` | `xrt_session` (event polling) |
| `ipc_client_compositor.c` | `xrt_compositor_native` (see `struct ipc_client_compositor` at line 58, `ipc_client_swapchain` at 94) |
| `ipc_client_device.c` + `ipc_client_hmd.c` + `ipc_client_xdev.{c,h}` | `xrt_device` (input/output/feature) |
| `ipc_client_space_overseer.c` | `xrt_space_overseer` |
| `ipc_client_future.c` | `xrt_future` |
| `ipc_client_connection.{c,h}` | message channel setup + reconnect |

`ipc_client_interface.h` exposes `ipc_instance_create(&ii, &out_xinst)`; this is what `targets/openxr/target.c` calls in client mode.

## Server side

`ipc/server/`. Single process, multiple threads:

* `ipc_server_process.c` — main entry `ipc_server_main(argc, argv, *ismi)`. Builds the local `xrt_instance` (via `target_instance.c`), shows the debug GUI if compiled in, then enters the mainloop.
* `ipc_server_mainloop_linux.c` / `ipc_server_mainloop_windows.cpp` / `ipc_server_mainloop_android.c` — accept new clients; spawn a per-client thread.
* `ipc_server_per_client_thread.c` — per-client receive loop. Each loop iteration reads one framed message, dispatches it.
* `ipc_server_handler.c` — the dispatch table. Generated calls here.
* `ipc_server.h` — central `ipc_server` type + per-client `ipc_client_state` (the server's mirror of the client). `ipc_client_state` (line 91) holds:
  * the `xrt_session *xs` + `xrt_compositor *xc` created for this client,
  * `xscs[IPC_MAX_CLIENT_SWAPCHAINS]` + `swapchain_data[]`,
  * `xcsems[IPC_MAX_CLIENT_SEMAPHORES]`, `xfts[IPC_MAX_CLIENT_FUTURES]`,
  * `xspcs[IPC_MAX_CLIENT_SPACES]`,
  * which reference spaces / device features are in use,
  * the socket fd (`imc`),
  * shm handle.

`IPC_MAX_CLIENTS = 32` clients can attach simultaneously.

## Special handles (the non-trivial part)

For swapchains the IPC has to hand actual GPU handles across processes:

* **Linux**: DMABUF file descriptors and timeline semaphore fds, sent via `SCM_RIGHTS` ancillary messages.
* **Windows**: shared NT handles (`HANDLE` from `D3D11_RESOURCE_MISC_SHARED_NTHANDLE` or `VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_WIN32`), duplicated into the target process via `DuplicateHandle`.
* **Android**: `AHardwareBuffer` over Binder.

The send/recv helpers wrap this so the generated code doesn't need to think about it; see `util/u_handles.{c,h}` and the `xrt_graphics_*_handle_t` typedefs in `xrt_handles.h`.

## When the IPC layer is bypassed

* In-process targets (`XRT_FEATURE_IPC_CLIENT` off, default on Windows & Android) — `ipc/client/` is not compiled in at all; the OpenXR runtime DLL links the full stack.
* `service-lib` target — runs `ipc_server_main` inside the same process as some embedding app; useful for tests.
